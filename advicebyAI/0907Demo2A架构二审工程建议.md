# Demo2A Architecture Second-Review Engineering Advice

> Date: 2026-09-07
> Type: **AI engineering advice** — not third-party source fact, not an implementation authorization.
> Scope: propose minimal architecture corrections after an independent review of the v0.1 candidate and current EgoGlove evidence.

## 1. Recommendation

Keep v0.1 as the historic conceptual baseline, but do **not** approve Demo2A 5+1 implementation yet. Create a small, offline, schema-and-fixture-only freeze package first:

1. `RawObservation` and `ClockMappingArtifact` contracts;
2. calibration lifecycle/resolution contract;
3. topology segment/rigid-island declaration;
4. numerical coordinate/quaternion fixtures;
5. factor contract registry;
6. reason-coded failure taxonomy;
7. capture-level replay manifest/equivalence policy;
8. canonical hand-root neutral/reference calibration procedure;
9. 5+1 versus 10+1 observability/ground-truth experiment protocol.

This is intentionally narrower than implementing a solver, camera pipeline, PCB, FPC, VIO/SLAM, MANO, retargeting, RLDS/LeRobot, or a full runtime.

## 2. Why the gate is blocked

Current fixtures prove that Hand Token stays unchanged, FK21 is derived, missing values are not zero-filled, profile/provenance references resolve, and simple lineage is stable. They do not yet prove that a multimodal raw event has the right event time, belongs to a valid clock segment, uses a current calibration, activates a mathematically defined factor, or deterministically produces a canonical pose.

Proceeding before those contracts would likely force either:

- a backwards-incompatible redefinition of an existing semantic field; or
- a silent implementation convention that becomes hard to replay, compare, or migrate from 5+1 to 10+1.

## 3. State-design advice

Use five distinct categories:

- `z`: immutable raw events;
- derived measurements: calibrated orientation/landmark/flex/tactile features;
- `X_t`: current inferred pose/dynamic variables;
- `Theta`: calibration/model parameters;
- projections: FK/MANO/OpenXR/ROS/robot views.

Do not store sensor-to-bone transforms, morphology, joint axes, flex transfers, or clock mappings as if they were per-frame measured pose. Do not label a prior-filled joint as measured. Public velocity is optional; if emitted, state whether it is measured, estimated, or filtered. Internal bias/velocity/acceleration can exist in a solver without becoming mandatory public output.

## 4. 5+1 and 10+1 advice

Maintain one additive schema. Demo2B should add five `secondary` sensor entries only; it should not change Demo2A IDs or meanings.

Before selecting physical placement, freeze `segment_assignment`, `rigid_island_id`, mounting class, and required calibration. The real hypothesis is not “10+1 is better”; it is:

> Secondary IMUs reduce uncertainty only when they observe a distinct calibrated rigid segment with adequate timing and excitation. Secondary IMUs on the same rigid island may contribute negligible rank gain.

Test the hypothesis using a common session and calibration protocol, repeated donning, single-finger hinge motions, coordinated motion, pure wrist yaw, fast motion, visual occlusion, and sensor dropout. Report uncertainty/observability and repeatability before any accuracy claim; use a ground-truth fixture before MAE/MPJPE claims.

## 5. Calibration advice

Treat calibration as versioned, typed evidence with scope and expiry. A calibration resolver should return one of `valid`, `invalid`, `expired`, `missing`, `unverified`, or `research_required`; factors must react explicitly.

The most urgent physical decisions before hardware are:

- hand-root neutral/reference procedure;
- sensor-to-bone placement and whether each mount is actually rigid;
- camera-to-wrist IMU spatial/temporal calibration plan;
- re-donning/flexible-FPC invalidation policy;
- flex/tactile baseline and spatial calibration procedure;
- clock segment/reset/wrap policy.

## 6. Timing advice

Preserve source event time and host-receive time separately. A simple affine map is acceptable only over an evidenced valid segment; mapping residual/uncertainty and reset/wrap behavior must be captured. Do not force all sensors to a common rate before fusion. Store interpolation, resampling, and latency compensation as derived transformations.

For camera, landmark time is exposure/event time or a declared estimate—not inference completion time. Keep visibility, occlusion, blur, rolling-shutter/readout, dropped-frame, and timing uncertainty as quality information.

## 7. Solver advice

A confidence-gated complementary/Slerp baseline is acceptable as a bounded Demo2A baseline. It must advertise exactly which state variables/factors it supports. It must not define Canonical State semantics or pretend to be a general nonlinear optimizer.

The architecture should permit a future fixed-lag/sliding-window optimizer only by sharing the raw observation, calibration, clock, factor, and output contracts. Choosing GTSAM/Ceres or any runtime dependency remains deferred.

## 8. License advice

Maintain separate records for code, models/checkpoints, datasets, hardware design, simulator data, and robot assets. FSGlove has no established repository reuse license; MANO is non-commercial/non-redistributable; FlexiTac hardware is CC BY-NC; MediaPipe model/data terms are per artifact. Do not build a commercial dependency plan from a repository’s README or code license alone.

## 9. Explicit non-actions

This advice does not authorize or recommend immediate implementation of a new hardware topology, PCBs/FPCs, firmware, full camera model, MANO fitting, GTSAM/Ceres, VIO/SLAM, robot retargeting, RLDS/LeRobot adapter, or production runtime.
